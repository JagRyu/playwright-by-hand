## W2D4 ❓ 답 (5분, 읽기만)

**1. 요소마다 가장 알맞은 메서드는?**

W2D3 에서 본 권장 순서를 요소 종류로 바꾸면 이렇다.

| 찾는 것 | 먼저 써 볼 것 |
|---|---|
| 버튼 · 링크 | `getByRole('button', { name: '...' })` · `getByRole('link', { name: '...' })` |
| 입력칸 | `getByPlaceholder('...')` (안내 글자가 있으면) |
| 화면 글자 확인 (제목 · 에러 문구) | `getByText('...')` |
| 같은 것이 여러 개 · 글자가 자주 바뀜 | `getByTestId('...')` |
| 위의 어느 것으로도 안 됨 | `locator('CSS')` |

정답이 하나가 아니다. 위에서부터 써 보고, **하나만 찾히면 거기서 멈춘다.**

**2. config 옵션과 메서드 목록은?**

외우지 않는다. 필요할 때 찾는다.

- VS Code 에서 `page.` 까지 치면 쓸 수 있는 메서드 목록이 뜬다. 메서드 이름 위에서 Ctrl+클릭하면 설명으로 간다.
- 공식 문서: playwright.dev/docs/api/class-page (page 메서드) · class-locator (쪽지 메서드) · test-configuration (config 옵션)
- config 옵션은 W6 에서 여러 개 다룬다. 지금은 `testIdAttribute` 하나면 충분하다.

**3. `--ui` 같은 실행 옵션은?**

`npx playwright test --help` 를 치면 전부 나온다. 우리가 쓰는 건 네 개다.

| 이렇게 치면 | 하는 일 |
|---|---|
| `npx playwright test cart` | 파일 이름에 `cart` 가 들어간 파일만 돈다 (W2D3) |
| `npx playwright test -g "결제"` | **테스트 이름**에 `결제` 가 들어간 테스트만 돈다 (오늘 새로) |
| `npx playwright test --headed` | 브라우저를 띄워서 돈다 (W2D1) |
| `npx playwright test --ui` | UI 모드 (W2D4) |

## 워밍업 (5분, 배운 것 복습)

**1.** 로그인 버튼의 HTML 이다. 지금까지 배운 메서드 중 이 버튼을 찾을 수 있는 것 **두 가지**를 쓰고, 권장 순서로는 어느 것을 먼저 쓰는지 적는다.

```html
<input type="submit" data-test="login-button" value="Login">
```

내 답: getByRole('button', {name: Login}) > getByTestId('login-button') > locator('[data-test="login-button"]')

**2.** 아래 줄은 실행하면 에러가 난다. (W2D3 에 두 번 했던 실수) 바르게 고쳐 쓴다.

```js
await expect(page).getByTestId('title').toBeVisible();
```

고친 줄: await expect(page.getByTestId('title')).toBeVisible();

## 개념 (5분): 오늘 쓸 화면

로그인 → 상품 담기 → 장바구니 → **Checkout** 버튼을 누르면 결제 정보 입력 화면이 나온다.

| 화면 | 주소에 들어가는 것 | 있는 것 |
|---|---|---|
| 결제 정보 입력 | `checkout-step-one` | 입력칸 3개(First Name · Last Name · Zip/Postal Code), `Continue` 버튼 |
| 결제 확인 | `checkout-step-two` | 주문 내용, `Finish` 버튼 |

칸을 비우고 `Continue` 를 누르면 빨간 에러 문구가 뜬다. **문구는 내가 직접 화면에서 찾는다.** (W2D2 처럼)

## 예측 퀴즈 (예측만 적는다. 파일은 아직 고치지 않는다)

> 예측 칸은 실행 뒤에도 고치지 않는다. 틀렸으면 아래에 `실제:` 를 따로 적는다.

**Q1.** 세 칸을 **모두 비우고** `Continue` 를 누르면, 에러 문구에 어느 칸 이름이 나올까? (확인은 **과제 1**)

내 예측: 순서대로 Error 를 뱉겠다고 정책을 정의했으면 First Name 에 해당하는 에러 문구가 나올 것이고, 세 칸 전부 Error 를 뱉겠다고 정책을 정의했으면 세 칸 모두 Error 문구가 나올 것이다.
실제: Error: First Name is required

**Q2.** 과제 2 까지 끝내면 `checkout.spec.js` 에 테스트가 2개 있다. `npx playwright test -g "결제"` 를 치면 몇 개가 돌까? (확인은 **과제 3**)

내 예측: 이름 비움이랑 정보 입력 2개 돌 것이다.

**Q3.** 테스트 1 의 에러 문구 확인을 **틀린 문구**로 바꾸면, 몇 초 뒤에 실패할까? (확인은 **과제 4**. W2D3 의 30초 · 5초 표를 떠올린다)

내 예측: getByText 로 확인한다면 5000ms 뒤에 실패한다.

### 과제 2. `checkout.spec.js` 혼자 쓰기 (새 파일)

`w2-first-test/checkout.spec.js` 를 만들고 `test(...)` 를 **두 개** 쓴다. 코드는 **codegen 없이** 손으로 쓴다. 각 줄의 찾는 방법은 위 ❓ 1번 표 순서대로 고른다. HTML 이 궁금하면 F12 로 본다.

| 테스트 이름 | 하는 일 | 마지막 확인 |
|---|---|---|
| `결제 - 이름 비움` | 세 칸 모두 비우고 `Continue` | 과제 1 의 에러 문구가 보인다 (`toBeVisible`) |
| `결제 - 정보 입력` | 세 칸 모두 채우고 `Continue` | 주소에 `checkout-step-two` 가 들어간다 (`toHaveURL`) |

> 로그인 · 담기 · 장바구니 · Checkout 네 줄을 테스트마다 또 써야 해서 불편하다. **그 불편함이 정상이다.** W5 에서 한 번만 쓰는 방법을 배운다.

다 쓰면 `npx playwright test` 로 전체를 돌린다.

결과(몇 passed): 7 passed

## 설명하기 (5분)

공식: ① 무엇인가 ② 왜 ③ 내가 본 증거. 물음표 없이 단정한다.

1. `checkout.spec.js` 에서 내가 고른 찾는 방법 중 **한 줄**을 골라, 왜 그 메서드를 골랐는지 쓴다. (증거: 그 줄이 하나만 찾아서 테스트가 통과했다는 결과, 또는 F12 에서 본 HTML) -> getByRole('button', { name: 'Continue' }) 로 Continue 버튼을 찾았다. HTML 이 <input type="submit" value="Continue"> 라서 역할은 버튼이고 이름은 value 의 Continue 다. 화면에서 사용자가 보는 그대로 찾을 수 있어서 권장 순서 1번인 getByRole 을 골랐다. 이 줄이 두 테스트에 모두 들어 있는데 strict mode 에러 없이 전체 7 passed 가 나왔으니, 이 이름의 버튼은 하나만 찾았다.

## W2 회고
