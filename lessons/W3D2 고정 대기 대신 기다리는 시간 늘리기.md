# W3D2: 고정 대기 대신 기다리는 시간 늘리기

> **손으로 짜는 Playwright** · W3 기다림과 확인 · 12/40회
> 형식: ❓ 답 5분 → 워밍업 5분 → 개념 10분 → 예측 퀴즈 → 손으로 치기 30분 → 설명하기 5분 → 기록 5분
> 오늘 새로 쓰는 것: `page.waitForTimeout(ms)`(나쁜 예로), `toBeVisible({ timeout: ms })`. 화면이 느릴 때 AI 는 "3초 쉬기"를 자주 넣는다. 그 코드가 왜 위험한지 직접 본다.

## W3D1 ❓ 답 (5분, 읽기만)

**1. 요소를 못 찾으면 몇 초까지 기다리나?**

시간은 찾는 메서드(`getByText` · `getByRole`)가 아니라, **그 줄에서 하는 일**이 정한다.

| 그 줄에서 하는 일 | 최대 기다림 | 이때까지 본 증거 |
|---|---|---|
| `click()` · `fill()` 같은 동작, `goto()` | 30초 (테스트 전체 제한) | W2D3 · W2D4 `Test timeout of 30000ms exceeded` |
| `await expect(쪽지).toBeVisible()` 같은 확인 | 5초 | W2D5 · W3D1 `Timeout: 5000ms` |
| `isVisible()` | **0초.** 지금 한 번만 본다 | W3D1 과제 3 `156ms` |
| `waitForTimeout(ms)` | 적은 만큼 **무조건** 쉰다 | 오늘 |

**2. `setContent`, `isVisible`, `toBe` 는?**

| 메서드 | 한 줄 뜻 |
|---|---|
| `page.setContent(html)` | 주소로 가는 대신, 내가 준 HTML 글자를 페이지로 띄운다 |
| `쪽지.isVisible()` | 지금 보이면 `true`, 아니면 `false` 를 돌려준다 |
| `expect(값).toBe(값)` | 두 값이 같은지 한 번 비교한다. 화면과 상관없는 그냥 값 비교다 |

**3. `onclick` 과 `setTimeout` 은?**

| 부분 | 뜻 |
|---|---|
| `onclick="할일"` | 이 버튼을 누르면 `할일` 을 한다 |
| `setTimeout(() => 할일, 2000)` | 2000ms(2초) 뒤에 `할일` 을 한다. `() => 할일` 은 W1 의 화살표 함수다 |

`setTimeout` 은 W2D2 의 "함수를 넘기기"와 같은 모양이다. **언제 할지**(2000)는 `setTimeout` 이 정하고, **무엇을 할지**는 내가 넘긴 함수가 정한다.

**4. `exact` 는 어디에 붙나?**

**글자로 찾는** 메서드에 붙는다.

```js
page.getByText('Saved', { exact: true })
page.getByRole('button', { name: 'Save', exact: true })
page.getByPlaceholder('First Name', { exact: true })
page.getByLabel('Password', { exact: true })
```

`getByTestId` 에는 없다. 이름표는 처음부터 정확히 같아야 찾기 때문이다.

## 워밍업 (5분, 배운 것 복습)

**1.** 아래 두 줄 중 **기다리지 않는** 줄은 몇 번인가? (W3D1)

```js
await expect(page.getByText('Saved')).toBeVisible();          // ①
expect(await page.getByText('Saved').isVisible()).toBe(true); // ②
```

내 답: 2번

**2.** 화면 버튼 글자는 `Login` 이다. 아래 줄은 통과할까? (W3D1 개념 1)

```js
await page.getByRole('button', { name: 'login' }).click();
```

내 답: 통과한다.

## 개념 (10분)

### 1. 고정 대기: `waitForTimeout`

```js
await page.waitForTimeout(3000);   // 무조건 3초 쉰다
```

화면이 느려서 테스트가 실패하면 AI 는 이 줄을 자주 넣는다. 문제는 **화면 상태를 보지 않는다**는 것이다.

| 화면이 준비되는 시간 | `waitForTimeout(3000)` 뒤 `isVisible()` |
|---|---|
| 2초 | 통과. 하지만 1초를 그냥 버린다 |
| 7초 | 3초 뒤 한 번 보고 `false` → 실패 |

빠를 땐 시간을 버리고, 느린 날엔 실패한다. W3D1 에서 본 **flaky** 의 대표 원인이다. Playwright 공식 문서도 실제 테스트에는 쓰지 말라고 한다.

### 2. 느린 화면은 그 확인만 더 기다리게 한다

```js
await expect(page.getByText('Saved')).toBeVisible({ timeout: 10000 });
```

| 부분 | 뜻 |
|---|---|
| `toBeVisible({ ... })` | 확인에 옵션 객체를 넘긴다. `getByRole('button', { name })` 과 같은 모양이다 |
| `timeout: 10000` | 이 확인**만** 5초 대신 10초까지 기다린다 |

10초를 **채우는** 게 아니다. 보이는 순간 바로 통과한다. 고정 대기와 가장 크게 다른 점이다.

### 3. 오늘 쓸 연습 페이지

W3D1 페이지에 버튼을 하나 더 넣는다.

```js
const html = `
<button onclick="setTimeout(() => document.body.insertAdjacentHTML('beforeend', '<p>Saved</p>'), 2000)">Save</button>
<button onclick="setTimeout(() => document.body.insertAdjacentHTML('beforeend', '<p>Saved</p>'), 7000)">Slow Save</button>
`;
```

| 줄 | 뜻 |
|---|---|
| 첫 번째 `<button>` | W3D1 그대로. `Save` 를 누르면 **2초** 뒤 `Saved` 가 생긴다 |
| 두 번째 `<button>` | 숫자(`7000`)와 버튼 글자(`Slow Save`)만 다르다. 누르면 **7초** 뒤 `Saved` 가 생긴다 |

## 손으로 치기 (30분)

`w3-wait` 폴더에서 한다. 새 파일은 `timeout.spec.js` 다.

### 과제 1. 버튼 찾기 (Q1 확인)

1. `timeout.spec.js` 를 만들고 `import` 줄과 개념 3 의 `html` 을 넣는다.
2. 테스트 하나를 쓴다. 이름은 `저장 - 기다리는 확인`, 하는 일은 `setContent(html)` → `getByRole('button', { name: 'Save' })` 클릭 → `await expect(page.getByText('Saved')).toBeVisible()`.
3. `npx playwright test timeout` → 결과를 적는다.
   - 실제 결과: (`Error:` 줄 · `resolved to ? elements` · `aka` 뒤에 나온 대안 · 걸린 시간)
     - Error: locator.click: Error: strict mode violation: getByRole('button', { name: 'Save' }) resolved to 2 elements
     - 10 번줄
     -  1) <button onclick="setTimeout(() => document.body.insertAdjacentHTML('beforeend', '<p>Saved</p>'), 2000)">Save</button> aka getByRole('button', { name: 'Save', exact: true })
        2) <button onclick="setTimeout(() => document.body.insertAdjacentHTML('beforeend', '<p>Saved</p>'), 7000)">Slow Save</button> aka getByRole('button', { name: 'Slow Save' })
     - 197ms
4. `aka` 가 알려 준 대로 고치고 다시 돌린다.
   - 결과(몇 passed): 1 passed

### 과제 2. 고정 대기와 비교 (Q2 확인)

과제 1 의 테스트 **위에** 테스트를 하나 더 쓴다. 이 테스트는 "AI 가 쓴 코드 표본"이다.

| 테스트 이름 | 하는 일 | 마지막 확인 |
|---|---|---|
| `저장 - 고정 대기` | `setContent(html)` → `Save` 클릭(과제 1 에서 고친 모양) → `await page.waitForTimeout(3000)` | `expect(await page.getByText('Saved').isVisible()).toBe(true)` |

`npx playwright test timeout` → 결과를 적는다.
- 실제 결과: (몇 passed · 두 테스트의 걸린 시간)
  - 2 passed
    - 저장 - 고정 대기 (3.2s)
    - 저장 - 기다리는 확인 (2.5s)

### 과제 3. 느린 화면 기다리기

테스트를 하나 더 쓴다.

| 테스트 이름 | 하는 일 | 마지막 확인 |
|---|---|---|
| `느린 저장 - 늘린 확인` | `setContent(html)` → `Slow Save` 클릭 | `toBeVisible({ timeout: 10000 })` |

`npx playwright test timeout` → 결과를 적는다.
- 결과: (몇 passed · 이 테스트의 걸린 시간)
  - 3 passed (14.4s)
    - 저장 - 고정 대기 (3.2s)
    - 저장 - 기다리는 확인 (2.5s)
    - 느린 저장 - 늘린 확인 (7.6s)

### 과제 4. 고장 내기 (예측 → 실행 → 되돌리기)

1. 테스트 1(`저장 - 고정 대기`)의 클릭을 `Slow Save` 로 바꾸고 `npx playwright test -g "고정 대기"` 로 돌린다 (Q3 확인).
   - 실제 결과: (`Error:` 줄 · `Expected:`·`Received:` 줄 · 걸린 시간)
     - Error: expect(received).toBe(expected) // Object.is equality
     - 10번 줄
     - Expected: true / Received: false
     - 3.2s
2. `Save` 로 되돌리고 `npx playwright test` 로 **전체가 통과하는지** 확인한다. (`wait.spec.js` 까지 같이 돈다)
   - 결과(몇 passed): 5 passed

## 설명하기 (5분)

공식: ① 무엇인가 ② 왜 ③ 내가 본 증거. 물음표 없이 단정한다. **증거는 `실제 결과:` 칸의 숫자나 메시지를 그대로 옮긴다.** ("과제 N 에서 확인했다"만 쓰면 증거가 아니다)

1. AI 가 느린 화면 앞에 `await page.waitForTimeout(3000)` 을 넣었다. 통과시킬 것인가, 고칠 것인가? 고친다면 무엇으로? (증거: 과제 2 · 3 · 4 의 시간) -> 고친다. 'Save'버튼 클릭 시 'Saved' 문구가 표출되는데 7초 정도 소요되는 html 화면을 테스트할 때에 'await page.waitForTimeout(3000)' 으로 인해 테스트가 실패했다는 결과를 출력했다. 아직 어떻게 고치면 좋을진 모르겠지만, 특정 API의 호출 완료 시간까지 대기한다던지, toBeVisible({ timeout: 10000 }) 로 그 확인만 오래 기다리게 하면 Saved 가 보이는 순간 통과한다.
