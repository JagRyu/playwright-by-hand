# W3D5: 화면에 맞는 확인 고르기와 W3 마무리

> **손으로 짜는 Playwright** · W3 기다림과 확인 · 15/40회
> 형식: ❓ 답 5분 → 워밍업 5분 → 개념 5분 → 예측 퀴즈 → 손으로 치기 30분 → 설명하기 5분 → 기록·W3 회고 5분
> 오늘은 W3 에서 배운 확인을 **표 하나**로 모으고, 연습 페이지가 아니라 **진짜 사이트(saucedemo)의 느린 사용자**에 써 본다. 새 메서드는 `toBeHidden()` 하나다.

## W3D4 ❓ 답 (5분, 읽기만)

> 화면이 어떻게 동작하느냐에 따라 어떤 확인 메서드를 골라야 하는지 아직 정확히는 모르겠다.

**화면이 무엇을 하는지 한 문장으로 말하고, 표에서 그 줄을 고른다.**

| 화면이 하는 일 | 찾기 | 확인 | 배운 날 |
|---|---|---|---|
| 새 요소가 **생긴다** | `getByText` · `getByRole` | `toBeVisible()` | W3D1 |
| 있던 칸의 글자가 **바뀐다** | `getByTestId` | `toHaveText('...')` | W3D3 |
| 요소가 **사라진다** | `getByRole` · `getByText` | `toBeHidden()` | **오늘** |
| 주소가 **바뀐다** | (`page` 그대로) | `toHaveURL(/.../)` | W2D2 |
| 위의 일이 **5초보다 늦다** | 그대로 | 같은 확인 + `{ timeout: 10000 }` | W3D2 |

예를 들면 이렇다.

- "Save 를 누르면 `Saved` 가 뜬다" → **생긴다** → `toBeVisible()`
- "상태 칸이 `Ready` 에서 `Saved` 로 바뀐다" → **바뀐다** → `toHaveText('Saved')`
- "로그인하면 로그인 버튼이 없어진다" → **사라진다** → `toBeHidden()`

어느 줄을 골라도 모양은 W3D4 그림 그대로 `await expect( 찾기 ).확인()` 이다. 표에 없는 것을 쓰고 싶으면 `.` 을 찍고 `to` 까지 쳐서 자동완성 목록을 본다.

## 워밍업 (5분, 배운 것 복습)

**1.** W3D4 에서 본 것을 떠올려 빈칸을 채운다.

- flaky 테스트는 코드를 바꾸지 않았는데 ( 실행 때마다 테스트 결과가 달라지는 ) 테스트다.
- `--retries=2` 로 돌린 결과의 `flaky` 는 처음엔 ( 실패 ) 했는데 다시 돌리니 ( 통과 ) 한 테스트 수다.

**2.** 위 ❓ 답 표를 보고, 아래 화면에 쓸 **확인**을 하나씩 적는다.

- ① 장바구니에 담으면 오른쪽 위에 숫자 `1` 이 생긴다: toBeVisible
- ② 버튼 글자가 `Add to cart` 에서 `Remove` 로 바뀐다: toHaveText
- ③ 결제 완료 후 주소에 `checkout-complete` 가 들어간다: toHaveURL

## 개념 (5분)

### 1. 느린 사용자: `performance_glitch_user`

saucedemo 에는 일부러 느리게 만든 사용자가 있다. 비밀번호는 같은 `secret_sauce` 다.

- `standard_user` 로 로그인하면 상품 화면이 금방 뜬다.
- `performance_glitch_user` 로 로그인하면 **화면이 5초쯤 멈췄다가** 상품 화면이 뜬다.

`toBeVisible()` 의 기본 기다림은 **5초**다 (W3D2). 진짜 사이트에서 이 경계를 넘으면 어떻게 되는지 본다.

### 2. 새 확인: `toBeHidden()`

```js
await expect(page.getByRole('button', { name: 'Login' })).toBeHidden();
```

| 부분 | 뜻 |
|---|---|
| `page.getByRole('button', { name: 'Login' })` | 찾기: 로그인 버튼 쪽지 |
| `toBeHidden()` | 확인: 그 요소가 **안 보이게 될 때까지** 기다린다. 기본 5초 |

`toBeVisible()` 의 반대다. 화면에서 아예 없어져도, 있는데 가려져도 통과한다.

## 예측 퀴즈 (예측만 적는다. 파일은 아직 고치지 않는다)

> 예측 칸은 실행 뒤에도 고치지 않는다. 틀렸으면 아래에 `실제:` 를 따로 적는다.
> 칸마다 하나를 고른다.

세 테스트는 모두 과제 1 에서 쓴다.

**Q1.** `느린 로그인 - 상품 화면`(느린 사용자로 로그인 → `await expect(page.getByText('Products')).toBeVisible()`)을 `--repeat-each=5` 로 돌리면? (확인은 **과제 2**)

- 통과 횟수(0번 / 1~4번 사이 / 5번 중): 1~4번
- 실패한다면 메시지(`Timeout: 5000ms` 줄 / `Expected:`·`Received:` 줄 중):
  - Timeout: 5000ms
  - Expected: Products
  - Received: null
- 실제: 
  - Timeout: 5000ms
  - Expected: visible
  - Error: element (s) not found

**Q2.** Q1 의 확인에 `{ timeout: 10000 }` 을 넣고 다시 `--repeat-each=5` 로 돌리면? (확인은 **과제 3**)

- 통과 횟수(0번 / 1~4번 사이 / 5번 중): 5번
- 한 번에 걸린 시간(1초 안팎 / 5~6초 / 10초 이상 중): 5~6초

**Q3.** `로그인 후 - 로그인 버튼 사라짐`에서 `click()` 줄을 주석으로 막고 돌리면? (확인은 **과제 4**)

- 결과(통과 / 실패 중): 실패
- 걸린 시간(1초 안 / 5초쯤 / 30초쯤 중): 5초쯤
- `Received:` 값(`visible` / `hidden` 중): visible

## 손으로 치기 (30분)

`w3-wait` 폴더에서 한다. 새 파일은 `glitch.spec.js` 다. 진짜 사이트라 `page.goto('https://www.saucedemo.com')` 로 시작한다 (`w2-first-test/login.spec.js` 와 같다).

### 과제 1. 두 테스트 쓰기

| 테스트 이름 | 하는 일 | 마지막 확인 |
|---|---|---|
| `느린 로그인 - 상품 화면` | `goto` → Username 에 `performance_glitch_user` → Password 에 `secret_sauce` → `Login` 클릭 | `await expect(page.getByText('Products')).toBeVisible();` |
| `로그인 후 - 로그인 버튼 사라짐` | `goto` → Username 에 `standard_user` → Password 에 `secret_sauce` → `Login` 클릭 | `await expect(page.getByRole('button', { name: 'Login' })).toBeHidden();` |

- 두 테스트 모두 마지막 확인은 **표에 적힌 한 줄만** 쓴다. 주소 확인(`toHaveURL`)은 오늘 넣지 않는다.

`npx playwright test glitch` 로 한 번 돌린다.

- 결과(몇 passed · 몇 failed): 1 passed 1 failed
- 실패한 테스트 이름: 느린 로그인 - 상품 화면

### 과제 2. 느린 로그인 5번 돌리기 (Q1 확인)

1. `npx playwright test glitch -g "상품 화면" --repeat-each=5`
   - 실제 결과(몇 passed · 몇 failed): 1 passed 4 failed
   - 걸린 시간 하나: 
     - passed: 7.1S
     - failed: 5.7s (가장 적게 걸린 시간)
   - 실패 메시지의 `Timeout:` 줄과 그 아래 `Error:` 줄:
     -     Error: expect(locator).toBeHidden() failed
     -     Locator:  getByRole('button', { name: 'Login' })
     -     Expected: hidden
     -     Received: visible
     -     Timeout:  5000ms

> 명령에 `glitch` 를 꼭 넣는다. 빼면 다른 파일의 테스트도 골라진다 (W3D4).

### 과제 3. 기다리는 시간 늘리기 (Q2 확인)

1. `느린 로그인 - 상품 화면` 의 마지막 확인 줄 앞에 `//` 를 붙여 주석으로 남긴다. 그 아래에 `{ timeout: 10000 }` 을 넣은 줄을 새로 쓴다. (W3D2 과제 3 과 같은 모양)
2. `npx playwright test glitch -g "상품 화면" --repeat-each=5`
   - 실제 결과(몇 passed): 5 passed
   - 걸린 시간 하나: 5.9s

### 과제 4. 사라짐 확인 망가뜨리기 (Q3 확인)

1. `로그인 후 - 로그인 버튼 사라짐` 의 `click()` 줄 앞에 `//` 를 붙인다.
2. `npx playwright test glitch -g "사라짐"`
   - 실제 결과(통과/실패 · 걸린 시간): 1 failed / 5.5s
   - `Expected:`·`Received:` 줄:
     - Expected: hidden
     - Received: visible
3. `//` 를 지워 되돌리고, `npx playwright test` 로 **전체가 통과하는지** 확인한다. (`wait`·`timeout`·`status`·`flaky`·`glitch` 다섯 파일)
   - 결과(몇 passed): 11 passed

## 설명하기 (5분)

공식: ① 무엇인가 ② 왜 ③ 내가 본 증거. 물음표 없이 단정한다. **증거는 `실제 결과:` 칸의 숫자나 메시지를 그대로 옮긴다.**

1. 동료가 "느린 사용자 테스트가 실패하니까 클릭 뒤에 `waitForTimeout(6000)` 을 넣자" 고 한다. 어떻게 고치는 게 맞나? (증거: 과제 2 · 과제 3 의 passed 수와 걸린 시간) -> passed 에 소요된 시간이 5.8s ~ 6.0s 정도 소요되니 6000보다 큰 7000이면 어느정도 수용 가능할 것 같다. 
   1. 정답: toBeVisible({timeout: 10000}) 과 같은 메서드를 사용한다.

2. "로그인하면 로그인 버튼이 없어진다" 를 확인할 때 왜 `toBeHidden()` 을 골랐나? (증거: ❓ 답 표의 어느 줄인지 · 과제 4 의 `Received:` 값) -> '없어진다' 를 확인하는 메서드가 필요한 상황이다. toBeHidden 은 Expected와 Received 의 값을 visible/hidden 둘 중의 하나로 출력하기에 적절하다. 실제 과제 4 에서 Expected: hidden, Received: visible 결과를 확인했다.
