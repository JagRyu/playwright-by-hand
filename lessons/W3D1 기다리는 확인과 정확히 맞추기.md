# W3D1: 기다리는 확인과 정확히 맞추기

> **손으로 짜는 Playwright** · W3 기다림과 확인 · 11/40회
> 형식: 워밍업 5분 → 개념 10분 → 예측 퀴즈 → 손으로 치기 30분 → 설명하기 5분 → 기록 5분
> 오늘 새로 쓰는 것: `{ exact: true }`, `isVisible()`, `expect(값).toBe(값)`. W2D5 14행이 소문자인데도 통과한 이유를 풀고, **AI 가 자주 쓰는 "기다리지 않는 확인"** 을 직접 깨 본다.

## 워밍업 (5분, 배운 것 복습)

**1.** W2 에서 본 기다리는 시간이다. 빈칸을 채운다. (W2D3 · W2D5 과제 4 의 결과 칸에 있다)

- `click()` · `fill()` 같은 동작은 요소를 최대 30초 기다린다.
- `await expect(...).toBeVisible()` 같은 확인은 최대 5초 기다린다.

**2.** 아래 줄은 에러 없이 지나가지만 버튼을 누르지 않는다. (W2D2 login-fail 에서 겪은 것) 고쳐 쓴다.

```js
await page.getByRole('button', { name: 'Continue' }).click;
```

고친 줄: await page.getByRole('button', {name: 'Continue'}).click();

## 개념 (10분)

### 1. `getByText` 는 기본으로 느슨하게 찾는다

W2D5 `checkout.spec.js` 14행은 화면 문구(`First Name`)와 달리 `First name` 으로 적혀 있는데 통과했다. `getByText` 는 기본으로 이렇게 찾는다.

| 기본 (옵션 없음) | `{ exact: true }` 를 붙이면 |
|---|---|
| 대소문자를 무시한다 | 대소문자까지 같아야 한다 |
| 글자 **일부**만 맞아도 찾는다 (`'first name'` 도 찾음) | 글자 **전체**가 같아야 한다 |

```js
page.getByText('Error: First Name is required', { exact: true })
```

`getByRole` 의 `{ name: '...' }` 도 기본은 같은 방식이다. `exact` 도 똑같이 붙인다.

### 2. 확인에는 두 종류가 있다

| | 기다리는 확인 | 한 번 보는 확인 |
|---|---|---|
| 모양 | `await expect(쪽지).toBeVisible()` | `expect(await 쪽지.isVisible()).toBe(true)` |
| 하는 일 | 보일 때까지 **5초 동안 계속 다시 본다** | **지금 이 순간** 한 번 보고 `true`/`false` 를 돌려준다 |
| 화면이 2초 뒤에 바뀌면 | 2초 뒤 보이니 통과 | 아직 안 보이니 `false` → 실패 |

- `expect(값).toBe(값)` 은 두 값이 같은지 한 번 비교한다. 기다리지 않는다.
- 왼쪽을 **web-first 확인**이라고 부른다. Playwright 가 권하는 모양이다.
- 오른쪽은 AI 가 자주 쓴다. 화면이 빠를 때는 통과하다가 느린 날 실패한다. 이렇게 **같은 코드가 됐다 안 됐다 하는 테스트를 flaky** 라고 한다. (W3 에서 계속 다룬다)

### 3. 오늘 쓸 연습 페이지

saucedemo 는 너무 빨라서 차이가 안 보인다. 그래서 `Save` 를 누르면 **2초 뒤에** `Saved` 가 나타나는 작은 페이지를 직접 만든다.

```js
const html = `
<button onclick="setTimeout(() => document.body.insertAdjacentHTML('beforeend', '<p>Saved</p>'), 2000)">Save</button>
`;
```

- 이 `html` 은 **그대로 복사**해도 된다. (W1D4 의 `wait` 처럼 원리는 넘어간다) 읽을 곳은 끝의 `2000`(=2초) 하나다.
- `await page.setContent(html)` 은 주소로 가는 `goto` 대신, 이 글자를 페이지로 띄운다.

## 예측 퀴즈 (예측만 적는다. 파일은 아직 고치지 않는다)

> 예측 칸은 실행 뒤에도 고치지 않는다. 틀렸으면 아래에 `실제:` 를 따로 적는다.
> 경우를 나눠 생각해도 좋다. 다만 마지막에 **"나는 ○○ 에 건다"** 로 하나를 고른다.

**Q1.** `checkout.spec.js` 14행(`'Error: First name is required'`, 소문자 n)에 `{ exact: true }` 만 붙이면 통과할까? 실패하면 몇 초 뒤일까? (확인은 **과제 2**)

내 예측: 실패할 것이다. getByText 이니 30초까지는 확인하려고 할 것이다.
실제: 실패한다. expect 줄이라 5초 소요된다.

**Q2.** 연습 페이지에서 `Save` 를 누르고 바로 `expect(await page.getByText('Saved').isVisible()).toBe(true)` 를 하면? (확인은 **과제 3**)

내 예측: 바로 직후에는 false 로 표출될 것이다. 'Save' 버튼 클릭 시 2초뒤에 'Saved'로 변환되는데, toBe(true)는 클릭 바로 직후를 보기에 그 사이에는 false 일 것이다.

**Q3.** `html` 의 `2000` 을 `7000` 으로 바꾸면, 기다리는 확인(`toBeVisible`) 테스트는 어떻게 될까? (확인은 **과제 4**)

내 예측: 5초후에 실패를 뱉을 것이다.

## 손으로 치기 (30분)

### 과제 1. W3 폴더 준비

`playwright-by-hand` 폴더(맨 위)에서 터미널로 친다.

```
mkdir w3-wait
copy w2-first-test\package.json w3-wait\
copy w2-first-test\playwright.config.js w3-wait\
cd w3-wait
npm install
```

`w3-wait` 안에 `node_modules` 가 생기면 끝이다. (브라우저는 W2 때 받아 둔 것을 그대로 쓴다)

### 과제 2. 14행을 정확히 맞추기 (Q1 확인)

`w2-first-test` 폴더에서 한다.

1. `checkout.spec.js` 14행의 `getByText(...)` 안에 `{ exact: true }` 를 붙인다. 글자는 아직 고치지 않는다.
2. `npx playwright test checkout` → 결과를 적는다.
   - 실제 결과: (`Error:` 줄 · 걸린 시간)
     - Error: expect(locator).toBeVisible() failed
     - Timeout: 5000ms
3. `First name` 을 화면 그대로 `First Name` 으로 고치고 다시 돌린다.
   - 결과(몇 passed): 2 passed

> 1 → 3 이 "느슨한 확인이 숨긴 오타를 정확한 확인이 잡아낸다"는 흐름이다. 끝나면 파일은 올바른 상태로 남는다.

### 과제 3. 두 종류의 확인 비교 (Q2 확인)

`w3-wait/wait.spec.js` 를 만들고 `test(...)` 를 **두 개** 쓴다. 맨 위 `import` 줄과 `html` 은 개념 3 그대로다.

| 테스트 이름 | 하는 일 | 마지막 확인 |
|---|---|---|
| `저장 - 기다리는 확인` | `setContent(html)` → `Save` 클릭 | `await expect(page.getByText('Saved')).toBeVisible()` |
| `저장 - 한 번 보는 확인` | `setContent(html)` → `Save` 클릭 | `expect(await page.getByText('Saved').isVisible()).toBe(true)` |

1. `w3-wait` 폴더에서 `npx playwright test` → 결과를 적는다.
   - 실제 결과: (몇 passed · 몇 failed · 실패한 테스트의 `Expected:`·`Received:` 줄 · 두 테스트의 걸린 시간)
     - 1 passed 1 failed
     - Error: expect(received).toBe(expected) // Object.is equality
      Expected: true
      Received: false
     - 걸린 시간
       - 저장 - 기다리는 확인 (2.6s)
       - 저장 - 한 번 보는 확인 (156ms) 
2. 실패한 줄을 지우지 말고 **앞에 `//` 를 붙여 주석으로 남긴다.** 그 아래에 기다리는 확인으로 고친 줄을 쓴다. 다시 돌린다.
   - 결과(몇 passed): 2 passed

> 주석으로 남긴 줄이 "AI 가 쓰면 고쳐야 하는 모양"의 표본이 된다.

### 과제 4. 고장 내기 (예측 → 실행 → 되돌리기)

1. `html` 의 `2000` 을 `7000` 으로 바꾸고 `npx playwright test -g "기다리는"` 으로 돌린다 (Q3 확인).
   - 실제 결과: (`Error:` 줄 · `Timeout:` 줄 · 걸린 시간)
     - Error: element(s) not found
     - Timeout: 5000ms
     - 5.2s
2. `7000` 을 `2000` 으로 되돌리고 `npx playwright test` 로 **전체가 통과하는지** 확인한다.
   - 결과(몇 passed): 2 passed

## 설명하기 (5분)

공식: ① 무엇인가 ② 왜 ③ 내가 본 증거. 물음표 없이 단정한다. 증거는 위 `실제 결과:` 칸에서 숫자나 메시지를 옮긴다.

1. `getByText` 에 `{ exact: true }` 를 붙이면 무엇이 달라지는가? (증거: 과제 2) -> exact: true 를 붙이면 대소문자와 글자 전체가 같아야 찾는다. 기본 getByText 는 대소문자를 무시하고 일부만 맞아도 찾아서, 화면은 Name 인데 name 으로 쓴 오타가 통과했다. 과제 2 에서 exact 만 붙이자 Timeout: 5000ms 로 실패했고, First Name 으로 고치자 2 passed 가 됐다.
2. AI 가 `expect(await page.getByText('Saved').isVisible()).toBe(true)` 로 확인을 썼다. 통과시킬 것인가, 고칠 것인가? (증거: 과제 3 의 두 테스트 시간 차이) -> 고친다. isVisible() 은 지금 이 순간을 한 번만 보고, toBeVisible() 은 보일 때까지 5초 동안 다시 본다. 과제 3 에서 한 번 보는 확인은 156ms 만에 Received: false 로 실패했고, 기다리는 확인은 2.6s 에 통과했다.
