# W4D1: 로그인을 한 군데로 모으기

> **손으로 짜는 Playwright** · W4 POM · 16/40회
> 형식: W3 정리 5분 → 회고 답 5분 → 워밍업 5분 → 개념 10분 → 예측 퀴즈 → 손으로 치기 25분 → 설명하기 5분 → 기록 5분
> W4 는 같은 코드를 여러 테스트에 반복해 쓰지 않는 법을 배운다. 오늘은 W1 에서 배운 **함수**와 **모듈**(`export`·`import`)만 쓴다. 새 문법은 없다. `class` 는 W4D2 부터다.

W3D5 커밋에 `w3-wait/glitch.spec.js` 가 **기본 확인**(`toBeVisible()`)인 채로 들어갔다. 이대로 `w3-wait` 전체를 돌리면 `느린 로그인 - 상품 화면` 이 실패한다.

1. `glitch.spec.js` 10행 앞에 `//` 를 붙이고, 그 아래에 `await expect(page.getByText('Products')).toBeVisible({ timeout: 10000 });` 를 쓴다. 8·9행의 `toBeHidden` 주석은 지워도 된다.
2. `w3-wait` 폴더에서 `npx playwright test` → 결과(몇 passed): 11 passed
3. 커밋한다: `W3D5: 느린 로그인 확인 고침`

> W3D5 과제 2·3 의 `실제:` 칸(`getByText('Products')` 로 다시 돌린 숫자)도 비어 있으면 이때 채운다.

## 개념 (10분)

### 1. 로그인 함수를 따로 파일에 둔다

새 파일 `login.js` 에 아래 함수를 쓴다.

```js
export async function login(page, user) {
  await page.goto('https://www.saucedemo.com');
  await page.getByPlaceholder('Username').fill(user);
  await page.getByPlaceholder('Password').fill('secret_sauce');
  await page.getByRole('button', { name: 'Login' }).click();
}
```

| 부분 | 뜻 |
|---|---|
| `export` | 다른 파일에서 `import` 로 가져다 쓸 수 있게 내놓는다 (W1D3) |
| `async function login(...)` | 안에서 `await` 를 쓰는 함수다 (W1D4). 그래서 부를 때도 `await` 를 붙인다 |
| `page` | 테스트가 받은 브라우저 페이지를 **넘겨받는** 자리다. 함수 안에는 `page` 가 없으니 밖에서 받아 와야 한다 |
| `user` | 사용자 이름 자리다. `'standard_user'`, `'performance_glitch_user'` 처럼 부를 때마다 바꿔 넣는다 |
| 안의 네 줄 | 지금까지 테스트마다 쓰던 로그인 네 줄 그대로다. `fill('standard_user')` 자리만 `fill(user)` 로 바뀌었다 |

### 2. 테스트에서 불러 쓴다

```js
import { test, expect } from '@playwright/test';
import { login } from './login.js';

test('로그인 - 상품 화면', async ({ page }) => {
  await login(page, 'standard_user');
  await expect(page.getByText('Products')).toBeVisible();
});
```

| 부분 | 뜻 |
|---|---|
| `import { login } from './login.js'` | 같은 폴더의 `login.js` 에서 `login` 함수를 가져온다 |
| `await login(page, 'standard_user')` | 로그인 네 줄을 한 줄로 부른다. 테스트가 받은 `page` 와 사용자 이름을 넘긴다 |

W1D3 에서 "`{ page }` 는 어디서 오나?" 를 물었었다. `test` 가 `page` 를 만들어 테스트에 넘기고, 오늘은 그 `page` 를 **우리가 다시 `login` 에 넘긴다.** 그래서 `login` 안의 `page.goto` 가 같은 브라우저 페이지를 움직인다.

### 3. 왜 모으나: 화면이 바뀌면 고칠 곳이 하나다

개발자가 입력칸 안내 글자를 `Username` 에서 `User name` 으로 바꿨다고 하자.

- 로그인 네 줄이 6곳에 있으면 → **6곳**을 찾아 고친다. 하나 빠뜨리면 그 테스트만 계속 실패한다.
- `login.js` 에 모아 두었으면 → **1곳**만 고친다.

이것이 W4 주제인 **POM**(Page Object Model, 화면마다 코드를 한 군데에 모으는 방식)의 출발점이다.

## 설명하기 (5분)

공식: ① 무엇인가 ② 왜 ③ 내가 본 증거. 물음표 없이 단정한다. **증거는 `실제 결과:` 칸의 숫자나 메시지를 그대로 옮긴다.**

1. 동료가 "로그인 네 줄쯤은 테스트마다 복사해 넣어도 되지 않나요?" 라고 한다. 왜 함수로 모으나? (증거: 과제 3 의 failed 수와 고친 파일 수) -> 과제 3 에서 로그인 네 줄을 사용하여 실패한 테스트 코드는 총 3개였지만, 동일한 코드를 사용하는 곳에서 Error 가 발견되어 수정이 필요하다면 1개의 파일만 고치면 되기에 더 효율적이다. 1개의 파일에 공통함수를 생성하지 않았다면 총 3개의 코드를 수정했어야 했다.

2. `login(page, user)` 에 `page` 를 넘기는 이유는 무엇인가? (증거: 개념 2 의 표. 함수 안에서 `page` 가 어디서 오는지) -> playwright page에서 온다. (잘 모르겠어요)
   1. claude 답: TV 리모컨에 비유하면 이래요. test 가 테스트마다 새 브라우저(TV)와 리모컨(page)을 만들어요. login 은 다른 방에 있는 사람이라 리모컨을 건네줘야 TV 를 켤 수 있어요.
